# 项目改进工作流 · Loop Engineering

更新:2026-10-16
适用范围:本仓库全部改进工作(功能收束、创新、重构、UI、修复、开源就绪)
状态:生效中(v1.1)

## 1. 这套流程解决什么问题

本项目是从上游接手的大型 monorepo(client 约 12 万行 / server 约 21.7 万行 TypeScript),改进方向多、周期长、跨会话进行。需要一种机制保证:

- 改进是**小步循环**而不是大爆炸:每轮(loop)目标单一、可独立验证、可独立回滚;
- 进程是**可见的**:任何人(包括未来的自己和新会话的 AI)打开进度日志就知道做到哪了;
- 取舍是**有依据的**:待办池里每项都有优先级和验收标准,砍掉什么、留下什么都有记录;
- 流程本身可迭代:发现流程不好用,就用一轮"流程"类任务修订流程(loop engineering 的自指部分)。

优先级判断的三个定位锚点(2026-10-15 与项目所有者确认):

1. **自用创作工具** —— 真实写完一本书的体验优先,主链稳定高于一切;
2. **个人开源作品** —— 可展示性、差异化、文档与发版质量;
3. **技术学习/作品集** —— 架构清晰度、可解释的工程亮点。

已确认的战略取舍:漫画/短剧工坊**降级为实验特性**;与上游(ExplosiveCoderflome)**完全独立发展**,重构不受上游兼容约束;创新覆盖写作质量、Agent 架构、交互可视化、成本效率四条线。

## 2. 三个文件

| 文件 | 职责 | 变更频率 |
|---|---|---|
| `docs/workflow/improvement-workflow.md`(本文) | 循环协议、质量门禁、红线 | 低(仅流程修订时) |
| `docs/workflow/BACKLOG.md` | 待办池:所有改进项、优先级、验收标准 | 中(每轮结束更新状态) |
| `docs/workflow/PROGRESS.md` | 进度日志:每轮一条记录 | 高(每轮必写) |

**新会话续跑方法**:读 PROGRESS.md 最新 1–2 条 + BACKLOG.md 的"轮次入口建议",即可接着干,不需要重新通读全仓库。

## 3. Loop 协议:一轮的生命周期

一轮(loop)是改进的最小交付单位,按 6 步走:

### L0 · 选题

- 从 BACKLOG 选一项(或一组强相关的小项);优先 P0/P1。
- 无法判断时问项目所有者;涉及方向性取舍(删功能、改定位)必须所有者拍板并把结论记入 PROGRESS。
- 预计跨多次会话的长轮,选题后先在 PROGRESS 开一条 `[/]` 进行中记录。

### L1 · 计划

- 写清楚:目标、范围(动哪些文件)、验收标准、风险、验证方式。
- 小轮:上述内容写进 PROGRESS 条目即可,不另开文档。
- 大轮(跨模块、改契约、动数据库 schema):先在 `docs/plans/` 写计划文档再动手。
- 中途发现工作量超出预估 2 倍以上:**停下**,在 BACKLOG 登记拆分,不硬扛、不悄悄扩大范围。

### L2 · 实现

- 尽量 TDD:先写/改测试再改实现(测试位于 `server/tests/`、`client/tests/`)。
- 一次只做选题范围内的事;顺手发现的问题记入 BACKLOG,不混进本轮(极小的顺手修可在 PROGRESS 注明)。
- 尊重仓库现有约定,尤其 `docs/wiki/architecture/` 里的模块边界(drama/adaptation 防腐层、prompt 注册规则等)。
- UI/前端轮次另须遵守:设计以 `docs/design/product-ui-design-system.md` 为准,可视化以 `docs/design/visualization-stack.md` 的栈纪律为准(不新引依赖、渲染归 React、懒加载),不新增 shadcn 组件。

### L3 · 验证

- 必跑:`pnpm --filter @ai-novel/server test`(fast 套件)。触碰集成链路时加跑 `test:integration`。
- 触碰前端的轮次必跑 `pnpm --filter @ai-novel/client typecheck`,并启动 dev 手工过一遍相关页面;UI 轮次还要按 §5 的 UI 类别要求做明暗主题/响应式走查,截图或描述记入 PROGRESS。
- **验证没过不许标记完成** —— 要么修到过,要么回滚本轮改动并在 PROGRESS 记录原因。

### L4 · 记录

- 在 `PROGRESS.md` **顶部**(最新在上)插入本轮完整条目:目标、改动、验证、遗留、下一步。
- 更新 BACKLOG 状态标记(`[x]` / `[~]` / `[/]`)及验收备注;新发现的条目一并登记。

### L5 · 提交

- 一轮 = 一个或一组语义化提交;提交信息沿用仓库风格(中文 `修复:` / `新增:` / `优化:` / `文档:` 等),结尾附 `Co-Authored-By: Claude Code <noreply@anthropic.com>`。
- 提交前自查:无密钥、无 db 文件、无调试残留。
- 只推送 `main` 分支;**永远不要 `git push --all` / `git push --mirror`**(见 §6 红线 1)。

## 4. 质量门禁(Definition of Done)

一轮可标记完成,必须同时满足:

1. 验证通过(测试绿 / 手工验证有记录);
2. PROGRESS 有本轮完整条目;
3. BACKLOG 状态已更新;
4. 改动已提交;
5. 无关改动没有混进来。

## 5. 轮次类别与验证要求

| 类别 | 典型内容 | 额外要求 |
|---|---|---|
| bugfix | 修缺陷 | 先复现(测试或步骤);修复后测试覆盖该缺陷 |
| 重构 | 拆文件、解耦、移动代码 | 行为不变:重构前后跑同一测试;禁止夹带功能 |
| 功能收束 | 实验化、删减、收敛入口 | 产品取舍必须所有者确认过(结论记入 PROGRESS) |
| 创新 | 新能力(INN 条目) | 有验收标准才开工;先落 MVP,不一次做全 |
| UI | 页面视觉、主题、可视化、交互富化(UI 条目) | 遵循设计系统与可视化栈纪律;client typecheck 必过;明暗主题/响应式走查;只减不增硬编码色 |
| 流程 | 修订本工作流自身 | 单独成轮,修订理由写进 PROGRESS |

## 6. 硬性红线

1. **绝不 `git push --all` / `git push --mirror`** 到 github/gitee 远端 —— `refs/remotes/upstream/*` 携带上游历史遗留的他人 API key(db 备份文件),只允许推送 `main`。
2. 不提交任何 `*.db` / db 备份 / 含密钥文件。db 明文存密钥(`DatabaseSecretStore` 无加密),任何 db 副本严禁入库。
3. 大规模删改(删模块、重写历史)前:开分支或确认有备份。用 `git filter-repo` 重写历史时**不要用 `--path-glob '*.sqlite'`**(其 glob 会误删 `server/src/prisma/migrations.sqlite/` 目录)。
4. 轮次范围外的问题:记 BACKLOG,不顺手改。
5. 与上游完全独立发展:不合并上游;重构、改名、删代码不受上游兼容约束。

## 7. 自动化增强(可选)

对低风险、验收明确的条目(文档、纯重构、测试补充),可用 `/loop` 或 ralph-loop 自动驱动多轮。约束:

- 自动轮仍必须走 L3–L5(验证 + PROGRESS 条目 + 提交);
- 涉及产品取舍、删功能、数据库 schema 的条目**禁止**自动轮;
- 自动轮一次只跑一个 backlog 条目。

## 8. 开源就绪清单(仓库转公开前必须完成)

1. 清理本地 `refs/remotes/upstream/*` + `git gc --prune=now`,复检历史无旧 key(红线 1 的背景);
2. 全库密钥扫描(含 git 历史);
3. LICENSE / NOTICE / CLA 与上游及个人归属表述核对;
4. 品牌与命名定稿(项目名、README、介绍站、包名);
5. README 与 `docs/public` 对外表述审校。

## 9. 工作流自身的迭代

- 每 5 轮做一次流程回顾,或任何一次流程受阻时:用"流程"类轮次修订本文,修订理由写进 PROGRESS。
- 版本记录:v1(2026-10-15)建立;v1.1(2026-10-16)新增前端 UI 改进工作线:轮次类别加 UI 类、L2/L3 补 UI 规范与验证要求。
